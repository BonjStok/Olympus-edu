# Архитектура «Олимпуса»

Документ для разработчиков и тех, кто сопровождает систему. Описывает компоненты, путь запроса,
сессии, слой сервисов, контент и ключевые решения. Команды запуска – в
[DEVELOPMENT.md](DEVELOPMENT.md) и [DEPLOYMENT.md](DEPLOYMENT.md), контракт API – в [API.md](API.md),
схема данных – в [DATA.md](DATA.md).

## 1. Компоненты

```text
                    MAX (iOS / Android / desktop / web.max.ru)
       чат-бот «Олимпус»                          мини-приложение (WebView / iframe)
            │ webhook: POST /max/webhook                    │ HTTPS: страница, /api/olympus
            ▼                                               ▼
┌───────────────────────────── Caddy :80/:443 (только production) ─────────────────────────────┐
│   /max/webhook* → bot:8090                     всё остальное → web:3000 (X-Real-IP)          │
└───────────┬───────────────────────────────────────────────┬──────────────────────────────────┘
            ▼                                               ▼
     bot (Node 22, bot/server.mjs)                web: vinext-приложение в workerd
     long polling или webhook                     (wrangler dev в Node 22)
     ─► https://platform-api2.max.ru              /api/olympus · /api/v1/* · /api/media/{id}
            │                                               │                     │
            │ SQL: читает records, progress;                │ SQL                 │ HTTP + Bearer RUNNER_TOKEN
            │ пишет bot_users, bot_reminders                │                     ▼
            └───────────────► PostgreSQL 17 ◄───────────────┘               runner:8080 (runner/server.mjs)
                            volume postgres_data                                  │ HTTP(S)
                                                                                  ▼
                                                                         Judge0 CE (внешний сервис)

Медиа учителя: эмуляция R2 внутри web, volume olympus_media (/app/.wrangler/state)
```

| Компонент | Где код | Образ / запуск | Порт | Роль |
|---|---|---|---|---|
| `web` | `app/`, `components/`, `lib/` | `Dockerfile` → `node scripts/docker-start.mjs` | `3000` (локально публикуется, в production – только внутри сети) | Интерфейс мини-приложения, RPC `/api/olympus`, API проверяющих `/api/v1`, выдача медиа `/api/media/{id}` |
| `postgres` | `drizzle/*.sql` | `postgres:17-alpine` | `5432` внутри Docker-сети | Контент, ревизии, сессии, прогресс, состояние бота |
| `runner` | `runner/server.mjs` | `runner/Dockerfile` | `8080` внутри сети | Проверяет запрос, отправляет код в Judge0, сравнивает вывод с тестами. Сам код не исполняет |
| `bot` | `bot/` | тот же образ, что `web`, команда `node bot/server.mjs` | `8090` внутри сети | Чат-бот MAX: приветствие, ближайшие олимпиады, прогресс, кнопки открытия мини-приложения |
| `caddy` | `Caddyfile` | `caddy:2.10-alpine`, только `compose.production.yaml` | `80`, `443` (+ `443/udp`) | HTTPS-сертификат, заголовки безопасности, маршрутизация webhook |
| Judge0 CE | не в репозитории | разворачивается отдельно | – | Песочница: компилирует и запускает код ребёнка |

Служебные сервисы Compose с профилем `tools` (`backup`, `restore`, `media-backup`) запускаются
вручную и описаны в [DEPLOYMENT.md](DEPLOYMENT.md#8-резервные-копии-и-восстановление).

## 2. Веб-приложение: из чего собрано

- **Фреймворк.** Next.js-совместимый App Router на [vinext](https://www.npmjs.com/package/vinext)
  (`vinext 1.0.0-beta.5`, Vite 8, React 19). `pnpm build` = `scripts/compile-content.mjs` +
  `vinext build`, результат – каталог `dist/` с серверной частью для Cloudflare Workers и
  конфигурацией `dist/server/wrangler.json`.
- **Среда выполнения.** В контейнере `web` работает `wrangler dev --local` (`scripts/docker-start.mjs`):
  серверный код исполняется в `workerd` – локальной среде Cloudflare Workers – внутри обычного
  Node-контейнера. Никакого облака Cloudflare не используется: `CLOUDFLARE_CF_FETCH_ENABLED=false`,
  `WRANGLER_SEND_METRICS=false`.
- **Медиа.** Привязка R2 `BUCKET` (`vite.config.ts`) эмулируется локально и хранится в
  `/app/.wrangler/state` (volume `olympus_media`). Подробнее – [MEDIA.md](MEDIA.md).
- **Интерфейс.** Одна страница `app/page.tsx` рендерится только на клиенте (компонент
  `components/olympus/App.tsx`). Навигация – вкладки «Главная», «Олимпиады», «Учёба», «Пробники»,
  «Я» и стек вложенных экранов; состояние зеркалится в `location.hash` (`#/calendar/event/<id>`,
  `#/learn/topic/<id>/practice/2`, `#/admin/olympiads`), поэтому работают «Назад» браузера,
  системная кнопка «Назад» MAX и ссылки. Компоненты – `@maxhub/max-ui` 0.5 плюс собственные.
- **MAX Bridge.** `app/layout.tsx` подключает `https://st.max.ru/js/max-web-app.js` синхронным
  `<script>`, до старта приложения. Обёртка – `lib/client/max-bridge.ts`; вне MAX все вызовы
  безопасно ничего не делают. Что именно используется – [MAX-INTEGRATION.md](MAX-INTEGRATION.md).

### Структура серверного кода

```text
app/api/**/route.ts        тонкие адаптеры Next-маршрутов: только вызывают обработчики из lib/api
lib/api/olympus/           RPC мини-приложения
  dispatcher.ts            GET = bootstrap, POST = { action, ... }; Origin, Content-Type, лимиты тела
  context.ts               контекст запроса и уровни доступа public / session / admin
  handlers/*.ts            session, learning, tasks, mocks, admin – по файлу на область
lib/api/v1/                API проверяющих (контракт openapi.yaml): handler.ts, routes.ts
lib/services/              бизнес-логика, общая для /api/olympus и /api/v1
lib/server/                инфраструктура: env, db, http, errors, session, max-auth, rate-limit, validate, crypto
lib/content/validate.mjs   правила контента – одна реализация для сборки, админки и sync-content
lib/domain/types.ts        общий контракт сервера и клиента: записи, прогресс, RPC, коды ошибок
lib/domain/achievements.mjs  правила медалей и звёзд, общие для интерфейса, сервера и бота
lib/client/                клиент RPC, MAX Bridge, безопасное хранилище, человеческие тексты ошибок
lib/ui/                    чистые функции интерфейса: календарь, CSV, прогресс, навигация, даты
components/olympus/        React-экраны (дети и режим учителя)
```

Правило слоёв: маршрут → обработчик (`lib/api/...`) проверяет тело запроса валидаторами
`lib/server/validate.ts` → сервис (`lib/services/...`) выполняет логику и пишет в БД. Ошибки –
только `ApiError` с кодом из `ApiErrorCode`; любое другое исключение превращается в `500` с общим
текстом, подробности уходят в лог.

## 3. Путь запроса

### 3.1 Открытие мини-приложения

1. MAX открывает URL мини-приложения. В мобильных клиентах – WebView, в web.max.ru – `<iframe>`
   с атрибутом `credentialless`. В URL MAX передаёт подписанные данные запуска (`WebAppData`) и,
   если есть, `start_param`.
2. `max-web-app.js` создаёт `window.WebApp`; `captureLaunchParams()` запоминает `WebAppData` и
   `WebAppStartParam`/`startapp` до того, как роутер перепишет hash.
3. Клиент (`components/olympus/state/data.tsx`, функция `start`) при наличии `initData` вызывает
   `POST /api/olympus {action:"session", initData}`. Сервер проверяет подпись
   (`lib/server/max-auth.ts`), создаёт сессию `max:<id MAX>` и возвращает `sessionToken` и
   подписанный `startParam`.
4. `GET /api/olympus` (bootstrap) возвращает каталог (для ребёнка – темы и пробники целиком,
   олимпиады без описания, источника, даты проверки и картинки, а уроки и задания только
   заголовками: без текста уроков, условий, ответов и тестов; каталог ребёнка кэшируется в памяти
   процесса до изменения контента, см. [API.md §4.1](API.md#41-get-apiolympus--bootstrap)),
   весь прогресс пользователя, профиль, флаги `features`
   (`runner`, `max`, `reminders`, `botName`), `sessionToken` и `serverTime` (часы сервера для таймера
   пробника).
5. Уроки и задания темы подгружаются по требованию действием `topic-content`: ответы, разборы,
   подсказки и тесты задач в нём не отдаются. Описание олимпиады, строку «Проверено … · источник»
   и картинку экран олимпиады подгружает действием `olympiad` (один раз за сеанс).
6. Если пришёл `start_param` (`event_<id>`, `topic_<id>`, `mock_<id>`, `tab_<вкладка>`),
   `AppShell` открывает нужный экран (`lib/ui/navigation.ts`, `parseStartParam`).

Вне MAX (обычный браузер) шаг 3 пропускается: bootstrap без токена создаёт гостевую сессию
`guest:<uuid>`.

### 3.2 Действие ребёнка (пример: проверка ответа)

```text
PracticeView → api.call("check", {id, answer}) → POST /api/olympus
  dispatcher: Origin/Content-Type → loadSession → лимит тела → routes.check (access: session)
    → handlers/tasks.ts: валидация → services/tasks.checkTask
        requireRecord (скрытые/удалённые → 404) → grading.isCorrectNumber
        → saveProgress("task:<id>") → stars.maybeAwardPracticeStar
  ← { correct, output, practiceStar }
```

Для задания с кодом `checkTask` вызывает `services/runner.executeOnRunner` → `runner` →
Judge0; если `RUNNER_URL` не задан или runner/Judge0 недоступны, ответ – `503 RUNNER_UNAVAILABLE`
с текстом «Проверка программ сейчас не работает. Твой код сохранён – попробуй позже.»

### 3.3 Подключение к БД

`lib/server/db.ts`: одно подключение `pg.Client` на HTTP-запрос, открывается лениво при первом
запросе к БД и закрывается в `finally`. Общий `Pool` на уровне модуля использовать нельзя: в
`workerd` сокеты привязаны к запросу, который их создал. Многошаговые изменения (публикация,
импорт, слияние прогресса, завершение пробника, восстановление версии) выполняются в транзакциях
(`Db.transaction`).

## 4. Сессии и вход

| Тип | `user_id` | Как появляется | Срок |
|---|---|---|---|
| Гость | `guest:<uuid>` | первый bootstrap без действующего токена | 365 дней; пустые (без прогресса) удаляются через сутки |
| MAX | `max:<id пользователя MAX>` | действие `session` с `initData` | 30 дней; при каждом открытии в MAX выдаётся новая |
| Учитель | тот же `user_id` + флаг `admin` | действие `admin-login` с `ADMIN_PASSWORD` | права снимаются после 60 минут без действий учителя |
| `test_user` API | `test:evaluator` | `POST /api/v1/auth/login` | токен детерминированный, меняется только со сменой пароля |

**Где лежит токен.** Сервер принимает токен из заголовка `Authorization: Bearer` или из cookie
`olympus_session`; заголовок главнее. Клиент хранит токен в памяти и `sessionStorage` и шлёт его
заголовком. Причина – web.max.ru: мини-приложение открывается в кросс-сайтовом iframe с `credentialless`,
где cookie не сохраняются. Cookie остаётся запасным путём для обычного браузера: по HTTPS
`HttpOnly; Secure; SameSite=None; Partitioned`, по HTTP (локально) `HttpOnly; SameSite=Lax`.

**Хранение.** В таблице `sessions` лежит только SHA-256 токена (`lib/server/session.ts`,
`sessionKey`); миграция `0003_session_token_hash.sql` захэшировала выданные ранее токены. Дамп
базы не позволяет войти чужой сессией.

**Проверка MAX `initData`** (`lib/server/max-auth.ts`, алгоритм dev.max.ru/docs/webapps/validation):
пары `key=value` без повторов, `hash` ровно один; значения декодируются, `hash` убирается, пары
сортируются и склеиваются через `\n`; `secret = HMAC_SHA256("WebAppData", BOT_TOKEN)`; подпись
`hex(HMAC_SHA256(secret, строка))` сравнивается за постоянное время. Данные действительны 1 час
(допуск 30 секунд на расхождение часов), длина `initData` – до 8192 символов. `user.id` хранится
строкой без потери точности int64.

**Гость → MAX.** Если в момент входа через MAX у клиента гостевая сессия, её прогресс переносится в
`max:<id>` одной транзакцией (`mergeUserProgress`): флаги «решено», «прочитано», «участвую»
объединяются через ИЛИ, число попыток – максимум, звёзды сохраняют самую раннюю дату, настройки
сливаются по полям, черновики кода и попытки пробников – побеждает более новая запись. Строки и
сессии гостя удаляются. Любая другая прежняя сессия при входе через MAX отзывается.

**Учитель.** `admin-login` сверяет пароль с `ADMIN_PASSWORD` за постоянное время и **меняет токен
сессии** (`rotateSession`): токен, известный до входа, не получает прав учителя. Срок прав
продлевается с каждым действием учителя: после 60 минут без действий сессия снова обычная, а
действия учителя отвечают `403 ADMIN_EXPIRED` до нового входа.

**Защита от подделки запросов.** POST без заголовка `Authorization` (то есть с cookie или без
сессии) должен прийти с того же `Origin`, иначе `403 BAD_ORIGIN`. Тело – только
`application/json`.

**Лимит неудачных входов.** Один счётчик на вход учителя и `/api/v1/auth/login`: 10 ошибок за
15 минут с одного адреса блокируют вход на 15 минут (`lib/server/rate-limit.ts`). Адрес берётся
только из `X-Real-IP`, который в production выставляет Caddy. Счётчики хранятся в памяти процесса.

## 5. Контент: от файлов в репозитории до экрана ребёнка

```text
content/<kind>/*.json ──► scripts/compile-content.mjs ──► lib/seed.json ──► scripts/seed.mjs ──► records
   (редактируются в Git)   (validate.mjs: схема, связи,     (в образе)     (при старте web,      (PostgreSQL)
                            дубли олимпиад)                                   SEED_MODE)
                                                                                                   ▲
                             админ-панель: черновик / публикация / импорт (те же правила) ─────────┘
                             scripts/sync-content.mjs: перенос новой версии в живую БД ────────────┘
```

- **Типы записей:** `olympiads`, `topics`, `lessons`, `tasks`, `mock-tests`. Все они лежат в одной
  таблице `records` как JSON (`data`), рядом – черновик (`draft`) и флаг мягкого удаления.
- **Одни правила везде.** `lib/content/validate.mjs` – единственная реализация проверки. Её
  вызывают сборка (`compile-content`), сервер при сохранении и импорте из админки и
  `sync-content`. Ошибка в контенте останавливает `pnpm build` (и Docker-сборку). Правила – в
  [DATA.md](DATA.md#4-схема-контента).
- **Видимость.** Черновик никогда не показывается детям: у опубликованной записи дети видят `data`,
  у ни разу не опубликованной (`unpublished: true`) – ничего. Для не-учителя такие id и удалённые
  записи отвечают `404` во всех действиях.
- **Проекции для ребёнка** (`lib/services/content.ts`): задание до решения – без `answer`,
  `solution`, `hint`, `tests`; после завершения пробника – с ответом и разбором, но скрытые тесты не
  уходят клиенту никогда. Разбор и ответ вне пробника – только по явному действию `reveal`,
  подсказка – `hint`; для задания из идущего пробника оба отвечают `409 MOCK_IN_PROGRESS`.
- **История.** Перед каждой публикацией, удалением и изменением через `sync-content` прежняя
  версия копируется в `revisions`; восстановление возвращает её **черновиком**, чтобы старая версия
  не стала видна детям без явной публикации.

### Наполнение базы при старте (`SEED_MODE`)

`scripts/docker-start.mjs` перед запуском сервера выполняет `scripts/postgres-migrate.mjs`
(все `drizzle/*.sql` по порядку, каждая один раз, в транзакции) и `scripts/seed.mjs`
(под advisory lock `721849311`, в одной транзакции):

| `SEED_MODE` | Что делает |
|---|---|
| `bootstrap` (по умолчанию) | загружает `lib/seed.json` только в пустую базу; если записи уже есть, лишь отмечает бандл как загруженный – правки учителей не трогаются |
| `sync` | обновляет записи, чей хэш изменился с прошлого импорта; прежняя версия уходит в `revisions` |
| `off` | ничего не делает с контентом |

Тот же скрипт удаляет истёкшие сессии и гостевые сессии без прогресса старше суток – при старте и
затем каждые 6 часов. Для выборочного обновления живой базы (например, нового календаря) есть
`scripts/sync-content.mjs` с пробным прогоном по умолчанию – см.
[DEPLOYMENT.md](DEPLOYMENT.md#7-обновление-контента-и-календаря-в-работающей-базе).

## 6. Чат-бот

Отдельный процесс `bot/server.mjs` из того же образа. Получает события MAX webhook-ом (production,
через Caddy `/max/webhook*`) или long polling (локально), читает `records` и `progress`, пишет только
в свои таблицы `bot_users` и `bot_reminders`, открывает мини-приложение кнопками `open_app` с
`start_param`. Без `BOT_TOKEN` работает в режиме `disabled` и отвечает только на `/health`.
Подробно – [BOT.md](BOT.md).

## 7. Проверка программ

```text
web ──POST /execute {code, language, tests}──► runner ──POST /submissions──► Judge0 CE
    ◄──── {correct, output, passed, total} ───        ◄── опрос GET /submissions/{token} ──
```

- В web-контейнере код ребёнка не запускается никогда. Runner тоже его не исполняет: проверяет
  токен (`RUNNER_TOKEN`), язык, размеры, ограничивает параллельность (`RUNNER_MAX_CONCURRENT`,
  по умолчанию 4, иначе `429`), отправляет каждый тест в Judge0 с лимитами (CPU 2 с, wall 5 с,
  память 256 МБ, сеть выключена) и сам сравнивает вывод с ожидаемым.
- Скрытые тесты хранятся только на сервере; ребёнку показывается пример (`example`) и итог
  «Пройдено тестов: N из M». Подробности ошибок выполнения показываются только для первого теста
  (он же публичный пример), чтобы вывод программы не раскрыл скрытые входные данные.
- Если `JUDGE0_URL` не задан, runner стартует в режиме `degraded` (healthcheck зелёный), а проверка
  кода отвечает `503`; остальные сценарии работают. Незачтённые из-за этого ответы в пробнике
  получают статус `unchecked`, их можно перепроверить позже (`mock-recheck`). Подробно –
  [JUDGE0.md](JUDGE0.md).

## 8. Ключевые решения и компромиссы

| Решение | Почему | Цена |
|---|---|---|
| Контент как JSON в одной таблице `records`, а не отдельные таблицы на тип | Одна модель для сборки, импорта, черновиков, ревизий и бота; схема контента меняется без миграций БД | Целостность связей (тема урока, задания пробника) проверяет `validate.mjs`, а не внешние ключи; запросы по полям контента – через `data::jsonb` |
| Прогресс как пары `(user_id, key) → JSON` | Новые виды прогресса без миграций; слияние гость → MAX по ключам | Агрегаты (звёзды, медали) считаются в коде |
| Сессия в заголовке `Authorization`, cookie – запасной путь | web.max.ru открывает приложение в `credentialless` iframe, где cookie не сохраняются | Токен хранится в `sessionStorage`; при его потере пользователь MAX заново входит по `initData` автоматически, а прогресс гостя в обычном браузере держится на cookie этого браузера |
| Токены сессий в БД только как SHA-256 | Дамп или бэкап не дают войти чужой сессией | Токен нельзя «показать» повторно – только выдать новый |
| Отдельный runner и внешний Judge0 | Недоверенный код не исполняется рядом с данными; Judge0 – отдельная песочница с лимитами ресурсов и без сети | Judge0 нужно разворачивать отдельно, без него задачи с кодом не проверяются |
| Сидирование при старте контейнера, а не в запросах | Нет гонок и задержек в первом запросе; advisory lock защищает от параллельных стартов | Для обновления живой базы нужен отдельный шаг `sync-content` |
| Серверный таймер пробника (`ends`, запас 5 с) и `serverTime` в bootstrap | Нельзя продлить попытку, переведя часы на устройстве | Фоновой задачи нет: по окончании времени попытку завершает приложение, а если оно было закрыто – сервер завершит её при следующем сохранении или завершении |
| Лимитер входа в памяти процесса | Достаточно для одного контейнера `web` | При нескольких экземплярах `web` нужен общий счётчик (например, в PostgreSQL или Redis) |
| Один контейнер `web` на `wrangler dev --local` | Код совместим с Cloudflare Workers и одинаково работает локально и на VPS без облака | Масштабирование – только вертикальное или несколькими контейнерами за балансировщиком с учётом пункта выше |
| Напоминания бота выключены (`BOT_REMINDERS=off`) | Правила MAX (Требования, п. 1.5) разрешают сервисные сообщения только по договору | Функция готова, но не работает до согласования с MAX |
