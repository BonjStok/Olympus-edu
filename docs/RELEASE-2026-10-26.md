## Обновление существующей production-базы

Обычная загрузка `SEED_MODE=bootstrap` не заменяет записи в заполненной базе.
Поэтому релиз содержит одноразовую миграцию
`drizzle/0004_task_replacements_20261026.sql`. Штатный `scripts/docker-start.mjs`
применяет её перед bootstrap, без изменения серверного `.env`.

Миграция содержит фиксированные данные только десяти заданий. Она:

- сохраняет прежнее опубликованное содержимое изменяемых записей в `revisions`;
- сохраняет черновики учителя и не затрагивает прогресс, сессии и остальные записи;
- не восстанавливает задания, которые учитель удалил;
- добавляет отсутствующее задание только при наличии его действующей темы;
- не создаёт лишнюю ревизию, если задание уже имеет новое содержимое;
- согласует хеши импорта этих записей для серверов с `SEED_MODE=sync`;
- выполняется в одной транзакции и регистрируется стандартным механизмом миграций.

Повторный запуск контейнера не выполняет миграцию заново и сохраняет последующие правки учителя.
На пустой базе полный актуальный набор загружается обычным bootstrap.
Прежние отметки о решении заданий с сохранёнными идентификаторами остаются в прогрессе.

Данные SQL зафиксированы для этого выпуска: после публикации миграцию не перегенерировать.
Следующая замена заданий должна иметь отдельную миграцию с новым номером.

## Путь через CI/CD

1. Отправить подготовленную ветку в GitHub и открыть PR в `main`.
2. Дождаться проверок CI, включая quality, PostgreSQL integration, Docker/API/E2E и actionlint.
3. После merge CI опубликует web и runner в GHCR с SHA merge-коммита.
4. Штатный Deploy сохранит резервную копию базы, получит коммит и образы, перезапустит
   `olympus-production` и проверит готовность сервисов. Новые задания применит миграция.

Серверный `/opt/olympus/.env` остаётся локальным файлом. Сохранённое пользователем значение
`JUDGE0_PYTHON_LANGUAGE_ID=71` продолжает поступать в runner через `env_file: .env`.
Временный аварийный установщик Python для этого выпуска не используется.
Файлы production Compose, деплоя, переменных и зависимостей сохранены из базовой `main`.

## Приёмка на VPS после Deploy

Команды выполняются в Linux SSH-сеансе пользователем, имеющим доступ к Docker:

```bash
cd /opt/olympus
docker compose -f compose.production.yaml ps
docker compose -f compose.production.yaml exec -T runner node -e \
  "console.log('Python ID:', process.env.JUDGE0_PYTHON_LANGUAGE_ID)"
docker compose -f compose.production.yaml exec -T web node scripts/runner-smoke.mjs
docker compose -f compose.production.yaml logs --tail=100 web
```

Ожидаются `Python ID: 71`, `Olympus runner smoke test: OK` и запись о применённой миграции
при первом старте. В приложении проверить тему `info-5-02` и задачу «Парты для трёх кабинетов»,
а также тему `math-5-06` и задачу «Три броска монеты».
Наличие `/health` само по себе не подтверждает выполнение Python.

## Откат

Штатный deploy-скрипт откатывает образ при неготовности нового релиза и перед выпуском делает
резервную копию PostgreSQL. Откат образа не откатывает уже применённые данные миграции.
Новые задания совместимы с предыдущим приложением: формат записей, идентификаторы и типы сохранены.
Для возврата отдельных условий доступны сохранённые ревизии в режиме учителя.
Полное восстановление базы из резервной копии выполняется отдельно при необходимости и
затрагивает данные, появившиеся после создания копии.
